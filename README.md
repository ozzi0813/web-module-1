# Модуль 1. Рефакторинг та аналіз Web API

## 1. Аналіз вихідного коду та виявлені проблеми (Legacy-код)
У результаті аналізу початкового стану застосунку було виявлено наступні недоліки:
- **Монолітна структура**: Вся логіка (обробка HTTP-запитів, валідація даних, розрахунок загальної суми та збереження замовлень) знаходилася в одному файлі `app.js`.
- **Відсутність розділення відповідальностей (Separation of Concerns)**: Бізнес-логіка була тісно пов'язана з HTTP-шаром.
- **Низька розширюваність та складність тестування**: Ізольоване тестування окремих компонентів (наприклад, валідації чи розрахунків) було ускладнене без запуску HTTP-сервера.

## 2. Прийняті технічні рішення та нова архітектура
Застосунок було рефакторено із застосуванням **Layered Architecture (Багатошарової архітектури)**:

1. **Routes Layer (`src/routes/orders.router.js`)**:
   - Відповідає виключно за маршрутизацію HTTP-запитів та зв'язок ендпоінтів із відповідними методами контролера.
2. **Controller Layer (`src/controllers/orders.controller.js`)**:
   - Приймає об'єкти `req` та `res`, викликає відповідні сервіси та формує HTTP-відповіді із належними статусами (`200`, `201`, `204`).
3. **Service Layer (`src/services/orders.service.js`)**:
   - Інкапсулює всю бізнес-логіку: валідацію вхідних даних, вирахування `total`, генерацію унікальних ID та роботу з колекцією даних.
   - Використано структуру **`Map`** замість звичайного масиву для збереження замовлень у пам'яті, що забезпечує швидкодію $O(1)$ для операцій пошуку (`getOrderById`) та видалення (`deleteOrder`).
4. **Centralized Error Handling Middleware (`src/middlewares/error-handler.js`)**:
   - Єдиний централізований обробник помилок, який перехоплює виключення з сервісного шару та повертає стандартизовану структуру помилки (`VALIDATION_ERROR`, `ORDER_NOT_FOUND`).
